We replaced 40 cron jobs with one SQLite queue

By Mira Okafor · October 27, 2026 · 7 min read

Two years ago our scheduled work lived in forty crontab entries spread across twelve servers. Nobody could say from one place which jobs had run last night, and the only alert for a missed job was a customer asking why their monthly report never arrived.

This spring we moved every one of those jobs into a single table in SQLite. Workers on each server now ask the table for the next due job instead of waiting for cron to start them. The change took three weeks, and since then we have not lost a single run.

One table, four columns that matter

The queue lives in a single table, and every worker claims a row with one UPDATE ... RETURNING statement. The columns that matter are the job name, the time it is due, its state, and how many times it has been tried. Everything else, such as arguments or the last error message, is there for people reading the table, not for the scheduler.

UPDATE jobs SET state = 'running', attempts = attempts + 1
WHERE id = (SELECT id FROM jobs WHERE state = 'due' AND run_at <= unixepoch() ORDER BY run_at LIMIT 1)
RETURNING id, name, args;

Because the select and the update happen in one statement, two workers can never claim the same row. SQLite serialises writers, so the second worker simply sees the next due job. We did not need a lock server, a leader election, or a heartbeat table.

Failing well

When a job throws, the worker writes the error into the row and pushes its due time back. The delay doubles with each attempt, starting at thirty seconds. After the fifth failure the row moves to a held state, and a small page in our admin tool lists every held job with its last error and a button to try again.

Held jobs turned out to be the most useful part of the project. Before, a failing job failed silently every night until someone noticed. Now it fails five times and then waits in plain sight, which is a much better place for a problem to wait.

Where this stops working

This design is not a replacement for a real message broker. SQLite allows one writer at a time, so a service that enqueues thousands of jobs per second would spend most of its time waiting on the write lock. Our busiest day runs about four thousand jobs, which leaves plenty of room.

The file also has to live on a disk every worker can reach safely. We keep it on the one server that already ran our admin tool, and workers on other servers talk to it through a thin HTTP endpoint rather than opening the database over a network share.

What we would tell our past selves

Put the schedule where you can query it. Most of the value came not from the queue itself but from being able to answer, with one SELECT, which jobs ran, which are late, and which are stuck.
